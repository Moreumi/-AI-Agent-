# Delivery Address Change Policy v1

## 1. 목적

주문 완료 이후 고객이 배송지 변경을 요청했을 때,
현재 주문 상태와 배송 상태를 기준으로
배송지 변경 가능 여부를 판단하기 위한 정책이다.

배송지 변경 가능 여부 판단과
실제 배송지 변경 Action 실행은 분리한다.

---

## 2. 판단 기준

배송지 변경 가능 여부는 다음 두 상태를 기준으로 판단한다.

- `order_status`
- `delivery_status`

---

## 3. 주문 상태 기준

### `order_completed`

정상적으로 완료된 주문이다.

배송지 변경 가능 여부를 판단하기 위해
`delivery_status`를 추가로 확인한다.

### `order_canceled`

이미 취소된 주문이므로
배송지를 변경할 수 없다.

### `order_failed`

정상적으로 완료되지 않은 주문이므로
배송지를 변경할 수 없다.

### 정의되지 않은 주문 상태

자동으로 변경 가능 또는 불가능으로 판단하지 않는다.

`needs_review` 상태로 처리한다.

---

## 4. 배송 상태 기준

### `preparing_shipment`

배송준비중 상태이다.

배송지 변경이 가능하다.

단, 배송지 변경 가능 판정을 받았더라도
즉시 데이터를 변경하지 않는다.

새 배송지를 확인하고
사용자의 최종 승인을 받은 이후에만
배송지 변경 Action을 실행한다.

### `in_transit`

이미 배송이 시작된 상태이므로
배송지를 변경할 수 없다.

### `delivered`

배송이 완료된 상태이므로
배송지를 변경할 수 없다.

### 정의되지 않은 배송 상태

자동으로 변경 가능 또는 불가능으로 판단하지 않는다.

`needs_review` 상태로 처리한다.

---

## 5. Write Action 실행 원칙

배송지 변경은 실제 주문 데이터를 변경하는 Write Action이다.

따라서 다음 과정을 거친다.

```text
주문 조회
→ 배송지 변경 가능 여부 판단
→ 새 배송지 수집
→ 새 배송지 임시 저장
→ 사용자 최종 승인
→ Action 직전 상태 재확인
→ 배송지 변경
```

Policy에서 `changeable`로 판단되었다는 것만으로
배송지를 변경하지 않는다.

사용자가 명확하게 최종 승인한 경우에만
Write Action을 실행한다.

---

## 6. Action 직전 재검증

배송지 변경 가능 여부를 처음 확인한 이후에도
실제 Action이 실행되기 전까지 주문 상태가 변경될 수 있다.

예:

```text
최초 확인
preparing_shipment
→ 배송지 변경 가능

사용자가 새 주소 입력

배송 시작
preparing_shipment → in_transit

사용자 최종 승인
```

이 경우 최초 판단 결과만 사용해서
배송지를 변경하면 안 된다.

따라서 실제 Write Action 실행 직전에
현재 `order_status`와 `delivery_status`를 다시 확인한다.

현재 상태가 더 이상 변경 가능한 상태가 아니라면
Action을 실행하지 않는다.

---

## 7. 사용자 승인 원칙

배송지 변경은 고객의 주문 정보를 실제로 수정하는 기능이므로
사용자의 명확한 최종 승인을 필요로 한다.

다음 단계는 서로 구분한다.

```text
배송지 변경 가능 여부 판단
≠
새 배송지 입력
≠
사용자 승인
≠
Write Action 실행
```

사용자가 새 배송지를 입력했다는 사실만으로
배송지를 변경하지 않는다.

새 배송지는 State에 임시 저장한 뒤
사용자에게 변경 전·후 배송지를 안내하고
최종 승인을 요청한다.

사용자가 명확하게 승인한 경우에만
실제 배송지 변경 Action을 실행한다.

사용자가 변경을 거절한 경우에는
실제 주문 데이터를 수정하지 않고
배송지 변경 Flow를 종료한다.

승인 또는 거절 여부가 불명확한 경우에는
State를 유지하고 다시 확인한다.

---

## 8. State 사용

배송지 변경은 여러 사용자 입력에 걸쳐 진행되는 Multi-turn Flow이다.

배송지 변경 과정에서 다음 정보를 State에 저장한다.

- `pending_action`
- `candidate_orders`
- `selected_order_id`
- `pending_data`

새 배송지는 실제 주문 데이터에 즉시 반영하지 않고
다음과 같이 `pending_data`에 임시 저장한다.

```python
state = {
    "pending_action": "confirm_delivery_address_change",
    "candidate_orders": [],
    "selected_order_id": 10001,
    "pending_data": {
        "new_delivery_address": "서울시 강남구 테헤란로 123"
    },
}
```

사용자의 최종 승인이 확인되기 전까지
실제 주문의 `delivery_address` 값은 변경하지 않는다.

배송지 변경이 완료되거나
사용자가 변경을 거절하거나
Flow를 계속할 수 없는 오류가 발생한 경우에는
관련 State를 초기화한다.

---

## 9. 주문이 여러 건인 경우

고객에게 주문이 여러 건 존재하고
사용자가 특정 주문번호를 명시하지 않은 경우
Agent가 임의로 주문을 선택하지 않는다.

변경 가능한 주문 후보를 사용자에게 제시하고
사용자가 변경할 주문을 직접 선택하도록 한다.

사용자가 주문번호를 선택하면
해당 주문에 대해 배송지 변경 가능 여부를 다시 확인한다.

선택 가능한 후보에 포함되지 않은 주문번호를 입력한 경우에는
기존 선택 State를 유지하고
안내된 주문번호 중에서 다시 선택하도록 요청한다.

---

## 10. 처리 Flow

현재 배송지 변경의 전체 처리 Flow는 다음과 같다.

```text
사용자 배송지 변경 요청
↓
Intent Classification
↓
delivery_address_change
↓
주문 조회
↓
주문 특정 여부 확인

├─ 주문 여러 건
│  ↓
│  주문 선택 요청
│  ↓
│  사용자 주문 선택
│
└─ 주문 특정
   ↓

배송지 변경 가능 여부 Policy
↓
변경 가능 여부 판단

├─ 변경 불가
│  ↓
│  사유 안내
│  ↓
│  Flow 종료
│
├─ needs_review
│  ↓
│  추가 확인 필요 안내
│  ↓
│  Flow 종료
│
└─ changeable
   ↓

새 배송지 요청
↓
사용자 새 배송지 입력
↓
새 배송지를 State에 임시 저장
↓
변경 전 / 변경 후 배송지 안내
↓
사용자 최종 승인 요청

├─ 거절
│  ↓
│  실제 변경 없이 State 초기화
│
├─ 불명확
│  ↓
│  승인 확인 State 유지
│
└─ 승인
   ↓

Action 직전 주문 상태 재검증
↓
배송지 변경 가능 여부 재확인

├─ 더 이상 변경 불가
│  ↓
│  Action 실행하지 않음
│
└─ 변경 가능
   ↓

배송지 변경 Write Action
↓
변경 결과 반환
↓
State 초기화
↓
최종 사용자 응답
```

## 11. 현재 MVP 제한

현재 MVP에서는 사용자가 입력한 배송지에 대해
외부 주소 API를 이용한 실제 주소 유효성 검증은 수행하지 않는다.

사용자가 입력한 값이 비어 있지 않은 문자열인지 확인한 뒤
변경 예정 배송지로 사용한다.

실제 서비스에서는 향후
도로명주소 API 등의 주소 검증 기능을 추가할 수 있다.

또한 현재 State는 서버 메모리에 저장되므로
서버가 재시작되면 진행 중인 배송지 변경 대화 상태가 초기화된다.

실제 서비스에서는
사용자 또는 세션별 State를 영속적으로 관리하는 구조가 필요하다.
